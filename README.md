# Contador — Бухгалтерская система для Узбекистана

Мультитенантная SaaS-система двойной записи по **НСБУ №21** с AI-классификатором банковских операций.

**Стек:** Next.js · TypeScript · Prisma 6 · PostgreSQL 16 · OpenAI GPT-4o-mini · Tailwind CSS 4 · Decimal.js  
**Нормативная база:** НСБУ №1 (рег. МЮ №3544, с 01.01.2025), НСБУ №21 (рег. МЮ №3593, с 01.01.2025)  
**Последнее обновление:** 2026-07-03

---

| Приложение | Порт | Статус | Описание |
|-----------|------|--------|----------|
| **v2** (основная) | 3032 | ✅ Активна (Docker) | Документоцентричный учёт, импорт выписок, AI-классификация, закрытие месяца, Форма №1 + Форма №2 |
| **v1** (legacy) | 3030 | ⛔ Не запущена | AI-чат ввода проводок. Код есть в `src/`, контейнер остановлен, не развивается |

## Быстрый старт (v2)

### Разработка

```bash
cd /home/admin1/contador/v2
npm install
npx prisma generate
npm run dev        # http://localhost:3032/v2
```

### Продакшн (Docker Compose)

Проект развёрнут через `docker-compose.yml` (сервисы `db`, `admin`, `v2`), **не PM2**.

```bash
cd /home/admin1/contador

# Пересобрать и перезапустить после изменений кода
docker compose build v2 admin
docker compose up -d v2 admin

# Статус / логи
docker ps --filter "name=contador"
docker logs contador-v2 --tail 50
docker logs contador-admin --tail 50
```

### База данных

Миграции в `prisma/migrations/` (корень — БД `contador`, для v1/admin) и `v2/prisma/migrations/` (БД `contador_v2`) — это **сырые SQL-файлы**, проект не использует `prisma migrate deploy`/стандартный migration-history. Применяются вручную:

```bash
# Применить конкретную миграцию
docker exec <db-container> psql -U user -d contador_v2 -f /path/to/migration.sql

# Сверить схему с БД (покажет недостающие изменения)
cd v2 && npx prisma migrate diff \
  --from-url "postgresql://user:password@172.26.0.2:5432/contador_v2" \
  --to-schema-datamodel prisma/schema.prisma --script

# Prisma Studio
cd v2 && npx prisma studio

# Прямой доступ
psql postgresql://user:password@172.26.0.2:5432/contador_v2
```

⚠️ **Важно:** т.к. миграции не отслеживаются `prisma migrate`, после `git pull` **всегда** проверяйте `migrate diff` перед тем как полагаться на новые поля/таблицы — 2026-07-03 обнаружилось, что несколько миграций (в т.ч. таблица `ClosingJob` и колонки `Document.taxCalendarSyncStatus/Error`) были в коде неделями, но не применены к реальной БД, из-за чего падал каждый вызов `postDocument()`.

## Ключевые возможности (v2)

### Форма №1 — Бухгалтерский баланс
- Полная реализация строк 010–780 по НСБУ №21 и §2 спецификации
- Прямые SQL-агрегаты по `JournalEntry` — без ORM-цепочек
- Контрарные счета (0200, 4910, 2980, 8610/8620) обрабатываются корректно
- Незакрытый финансовый результат текущего года (`transitNet`) включается в строку 450
- Балансовый контроль: стр.400 = стр.780 (допуск ≤ 1 сум)

### Форма №2 — Отчёт о финансовых результатах
- Полная реализация строк 010–270 по НСБУ №21 и §3 спецификации
- Источник: дебетовые/кредитовые обороты по счетам 9xxx (исключая PERIOD_CLOSING)
- Строка 250: берётся из оборота 9810; если 0 — фолбэк на `TaxCalendarEvent`
- Помесячный разрез для графиков дашборда
- Корректная подпись ставки: `Налог на прибыль (15%)` или `Налог с оборота (N%)`

### Два режима налогообложения
| Параметр | НДС + налог на прибыль | Налог с оборота |
|----------|----------------------|-----------------|
| `taxRegime` | `VAT` | `TURNOVER_TAX` |
| `isVatPayer` | `true` | `false` |
| Ставка | НДС 12%, прибыль 15% | `turnoverTaxRate` (1–4%, настраивается) |
| Начисление | Дт 9810 → Кт 6410 | Дт 9810 → Кт 6410 (документ TURNOVER_TAX_ACCRUAL) |
| Форма №2 стр.250 | Дебет 9810 | Дебет 9810 |

### Импорт банковских выписок
- Форматы: 1CClientBankExchange (.txt), Excel (Asaka, Kapital, Ipak Yoli)
- SHA-256 дедупликация — повторный импорт безопасен
- Откат импорта по `importBatchId`

### AI-классификация операций
- Движок правил: INN → KEYWORD → AMOUNT_RANGE → TREASURY_ACCOUNT
- GPT-4o-mini, батчи до 20 транзакций, порог уверенности 70%
- Очередь уточнений с автосозданием правил из ответов пользователя

### Мастер закрытия месяца (7 шагов)
1. Импорт выписки
2. Классификация (AI + правила + уточнения)
3. Реестр и проверка документов
4. Начисления (ФОТ, амортизация, аренда)
5. Курсовые разницы — пользователь вручную вводит курс ЦБ и сумму разницы (сверяясь с банковской выпиской); backend проводит ровно введённую сумму по счёту 5210, без пересчёта
6. Сверка с Soliq (ЭСФ)
7. Финализация: расчёт налогов → PERIOD_CLOSING (9xxx→9910) → блокировка периода

### Годовое закрытие
```
POST /api/closing/year-end
```
Переносит чистую прибыль/убыток 9910 → 8710 (документ `YEAR_END_CLOSE`).  
Доступно только для декабря с уже закрытым периодом.

### Открытые позиции
- Авансы полученные/выданные, подотчёт (командировочные и общехозяйственные), депозиты, дивиденды к оплате
- Автоматический статус RISK по истечении дедлайна
- Дедлайны по умолчанию: 10 дн. (подотчёт), 30 дн. (авансы и прочие буферные счета), 365 дн. (депозиты, займы учредителей, дивиденды) — настраиваются на уровне организации в `/v2/settings/open-items-deadlines`

## Недавние изменения (2026-07-03)

Аудит + правки БД, кода и тестов. Полные детали — в истории коммитов и `prisma/migrations/*.sql`.

- **Критично:** применены пропущенные миграции к `contador_v2` (таблица `ClosingJob`, колонки `Document.taxCalendarSyncStatus/Error`, индексы `Payment`/`Rule`) — без них падал каждый `postDocument()`. То же для `contador` (admin/v1): убран лишний `TRANSIT` из enum `AccountType`.
- **Курсовые разницы (FX closing):** backend больше не пересчитывает свою сумму по остаткам счетов (раньше это игнорировало ввод пользователя и давало неверный знак для пассивных валютных статей). Теперь проводится ровно то, что пользователь ввёл на шаге 5.
- **`expressionEval.ts`:** движок выражений в шаблонах проводок не поддерживал строковые литералы (`'monthly'`) и `&&` — из-за этого документы `SUBSCRIPTION` и `CUSTOMS_DUTY` не могли быть проведены никогда. Исправлено.
- **`finalizePeriod()`:** при первом закрытии периода терялись начисления, сохранённые через wizard (создавался пустой `ClosingJob` вместо использования `Period.closingData`). Исправлено.
- **`POST /api/rules`:** не проверял на дубли — приводило к конфликтующим правилам автоклассификации для одного контрагента. Добавлена проверка + уникальный индекс в БД.
- **Security (admin-панель):** убраны hardcoded fallback для `ADMIN_PASSWORD`/`V2_DATABASE_URL`, убран приём пароля через query string.
- **`eslint.config.js`** — линт был полностью нерабочим (ESLint 9 без конфига), теперь работает.
- Очищены тестовые данные, утёкшие в реальную БД из-за отсутствующей очистки в интеграционных тестах (`real-user-simulation.test.ts`, `e2e-full-cycle.test.ts`) — обе теперь корректно удаляют созданные org/user в `afterAll`.
- **Курсовые разницы, вариант А закреплён:** backend использует ровно тот `difference`, что ввёл пользователь на шаге 5 (без пересчёта по остаткам).
- **+39 новых типов документов** (98 → 138) для покрытия НСБУ-21: безвозмездные поступления (ОС/НМА/материалы/товары/ЦБ через 8530), инвентаризация (излишки/недостачи/отнесение недостачи), резервный капитал и резервы предстоящих расходов, гранты/субсидии/членские взносы/налоговые льготы (8810–8890), переоценка товаров, оприходование товаров в пути, производственный цикл (материалы → производство → готовая продукция → списание себестоимости), финансовая аренда (лизинг), роялти, аккредитивы, депонирование зарплаты, проценты по депозиту, реклассификация долгосрочной задолженности в краткосрочную, чрезвычайные доходы/расходы. Все счета уже существовали в `seed-coa.ts` — не хватало только шаблонов проводки. См. `STAGE 4`/`STAGE 5` в `ensureBaseData.ts` и `src/__tests__/new-document-types.test.ts`.
- **Исправлен `expressionEval.ts` (второй раз за сессию):** унарный `!` в условиях (`"!useReserve"`) никогда не поддерживался токенайзером — падал с `Unknown character in expression: !`. Это была скрытая, ранее не пойманная ошибка в уже существующем `BAD_DEBT_WRITEOFF` (единственный тип, использовавший `!флаг` до сегодняшних правок).
- Осознанно **не** добавлены: забалансовые операции (001/002/007 — движок проводок пока не поддерживает односторонние/внебалансовые записи, нужна доработка `postingEngine.ts`), реорганизация/гудвилл, дисконтирование по займам, перемещение между складами (нет складского измерения в модели данных) — см. раздел «Функциональность» ниже.

## Тесты

Часть тестов (`e2e-full-cycle`, `real-user-simulation`, `fx-closing`, `seed` и др.) — интеграционные, бьют в реальную БД `contador_v2`. Вне Docker-сети нужно указать её напрямую через IP контейнера:

```bash
cd /home/admin1/contador/v2
npm run test        # Vitest, читает DATABASE_URL из v2/.env

# если контейнер БД недоступен по DNS-имени "contador-db":
DATABASE_URL="postgresql://user:password@$(docker inspect <db-container> --format '{{(index .NetworkSettings.Networks "contador_contador-net").IPAddress}}'):5432/contador_v2" npx vitest run
```

Покрытие: импорт, periods, dashboard API, P&L, cashflow, year-end, step4 validation, closing/reopen race, FX-переоценка, дедуп правил классификации, e2e полного цикла (начисления → закрытие → отчётность).

⚠️ Известная нестабильность: 3 теста в `e2e-full-cycle.test.ts` (Scenario B/C — GOODS_RECEIVED, INSURANCE_PAYMENT, SUBSCRIPTION) иногда падают между прогонами по неустановленной причине, не связанной с бизнес-логикой (подтверждено детерминированным кодом вокруг них). Требует отдельного расследования инфраструктуры тестов.

⚠️ Интеграционные тесты в `real-user-simulation.test.ts`/`e2e-full-cycle.test.ts` создают и удаляют свою org/user в каждом прогоне. Если тест упадёт настолько, что `afterAll` не выполнится (краш процесса, не просто failed assertion), в БД могут остаться тестовые организации "ООО Алга Технологии" / "ООО Тест E2E" — проверяйте `SELECT name FROM "Organization"` после массовых прогонов.
