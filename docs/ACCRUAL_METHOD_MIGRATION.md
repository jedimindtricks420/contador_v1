# Переход на накопительный метод — что нужно переделать в Contador

**Принцип:** доход и расход признаются в момент экономического события (отгрузка/получение, подтверждённое ЭСФ), а не в момент движения денег. Деньги без подтверждающего события — это актив/обязательство (буфер), не доход/расход. Единственное исключение — Отчёт о движении денежных средств (Cash Flow), он остаётся кассовым по своей природе везде в мире, это не нужно переделывать.

---

## 1. Доходная сторона — поступления от покупателей

**Сейчас:** `REVENUE_VAT`/`REVENUE_NO_VAT` признают доход (9030) и налог (6410) прямо в момент поступления денег на 5110.

**Должно быть:** деньги по умолчанию падают на 6310 (аванс), доход и налог признаются только когда подтверждена подписанная ЭСФ — отдельным, не-банковским документом `INVOICE_CONFIRMED`.

```
Деньги пришли:        Дт 5110 / Кт 6310           (как ADVANCE_RECEIVED сейчас)
ЭСФ подписана:        Дт 6310 / Кт 9030            (доход признан)
                       Дт 9030 / Кт 6410            (НДС) или Дт 9810/Кт 6410 (налог с оборота)
```

**Что менять:** `aiClassifier.ts` и `rulesEngine.ts` — поступление от покупателя по умолчанию классифицируется как `ADVANCE_RECEIVED`, не `REVENUE_VAT`, если для суммы не найдена подтверждённая ЭСФ. Новый тип `INVOICE_CONFIRMED` в `ensureBaseData.ts`. Новое поле `awaitingInvoiceSign` в `OpenItem`.

**Откуда подтверждение события:** Шаг 6 Wizard (сверка с soliq) — это основной, более надёжный канал обнаружения подписанной ЭСФ, чем ручное подтверждение пользователем. Ручное подтверждение — запасной путь, если соliq ещё не отразил.

## 2. Расходная сторона — оплата поставщикам (симметрично пункту 1)

**Сейчас (после сегодняшнего фикса):** `SUPPLIER_PAYMENT_GOODS/SERVICES/OTHER` признают расход (9120/9130/9430) прямо в момент оплаты с 5110.

**Должно быть:** расход признаётся в момент получения товара/услуги, оплата просто гасит уже существующий долг.

```
Товар/услуга получены:  Дт 9120 (или 9130) / Кт 6010    (расход признан, долг возник)
Оплата (любой месяц):   Дт 6010 / Кт 5110                (просто гасит долг, НЕ расход)
```

**Что менять:** новые типы `GOODS_RECEIVED`/`SERVICE_RECEIVED` (`MANUAL_ONLY`, пользователь вводит вручную, как договорились). Существующие `SUPPLIER_PAYMENT_GOODS/SERVICES/OTHER` должны измениться по смыслу — это уже не «расход», а «погашение долга», поэтому правильная проводка для них Дт 6010 / Кт 5110, без затрагивания 9120/9130/9430 напрямую. Расход появляется только через новый тип в момент получения.

**Входящий НДС (4410)** переезжает туда же — выделяется в момент `GOODS_RECEIVED`/`SERVICE_RECEIVED` (Дт 4410/Кт 6010 параллельно), не в момент оплаты. Сегодняшний фикс `SUPPLIER_PAYMENT_VAT` (4410 в момент оплаты) нужно пересмотреть по той же логике.

## 3. Маркетплейс / эквайринг (Payme-кейс)

**Уже частично описано в каталоге типов**, но завязано на пункт 1 — полная сумма оборота (9030) признаётся только когда подтверждена ЭСФ от площадки, а не в момент поступления уменьшенной суммы на счёт. До подтверждения — вся сумма (включая удержанную комиссию) висит как 6310, как обычный аванс.

```
Деньги пришли (196 000):     Дт 5110 / Кт 6310    (196 000)
ЭСФ от площадки подтверждена (на 200 000 оборота, 4 000 комиссия):
                               Дт 6310 / Кт 9030    (200 000 — полная выручка)
                               Дт 9430 / Кт 6310    (4 000 — расход на комиссию, закрывает остаток буфера)
```

**Автораспознавание:** по метке marketplace/Онлайн ККМ в файле soliq, и по списку известных контрагентов в настройках организации — оба способа уже зафиксированы в разговоре, нужно реализовать.

## 4. Зарплата — уже соответствует, без изменений

`SALARY_ACCRUAL` (начисление, признаёт расход 9420) и `SALARY` (выплата, просто гасит 6710) — это уже правильно реализованная накопительная пара. Используется как образец для остальных пунктов выше, ничего здесь менять не нужно.

---

## 5. Налоговый календарь — момент создания меняется

**Сейчас:** `TaxCalendarEvent` создаётся только в `finalizePeriod()`, при закрытии периода.

**Должно быть:** дополнительно создаётся в момент `INVOICE_CONFIRMED` — потому что подписание ЭСФ (и значит возникновение налогового обязательства) может произойти в любой день месяца, не только на закрытии.

**Что менять:** `closing.ts` — функция создания налоговых событий должна вызываться из двух мест, не одного.

---

## 6. Отчёты — фильтрация по семантике счёта, не по списку кодов

**Сейчас:** `closing.ts` и `pnl/route.ts` фильтруют доход/расход по жёстко прибитым спискам `accountCode`. Это уже создавало баг с 6010 один раз (сегодняшний фикс его частично закрыл точечно, добавив новые коды в списки).

**Должно быть:** после внедрения пунктов 1-2, расходные/доходные счета (9xxx) будут затрагиваться только через начисление, не через оплату — поэтому фильтрация по списку кодов 9xxx продолжит работать корректно без необходимости постоянно добавлять туда новые коды при каждом новом типе документа. Это естественное следствие правильной архитектуры, а не отдельная задача — но стоит зафиксировать как критерий проверки.

---

## 7. ОСВ и Форма №1 — счета 6310, 6010, 4410 должны иметь реальные остатки на любую дату

**Критерий готовности всего перехода:** на любую промежуточную дату закрытия, ОСВ должен показывать ненулевой остаток на 6310 (если есть неподтверждённые ЭСФ от покупателей) и на 6010 (если есть полученный, но неоплаченный товар) — это и есть видимая дебиторка/кредиторка, которой раньше в системе физически не было.

## Порядок реализации

```
1. Module 1 (Accrual Bridge) — доходная сторона, уже специфицирован отдельным файлом
2. Зеркальный модуль для расходной стороны — GOODS_RECEIVED/SERVICE_RECEIVED,
   пересмотр сегодняшнего фикса SUPPLIER_PAYMENT_GOODS/SERVICES/VAT
3. Маркетплейс/эквайринг — отдельный тип, зависит от пункта 1
4. Налоговый календарь — точка создания TaxCalendarEvent
5. Верификация через ОСВ на промежуточную дату — пункт 7 как финальный тест
```

## Что НЕ нужно переделывать

Cash Flow отчёт (`cashflow/route.ts`) — остаётся кассовым, это правильно везде в мире, включая НСБУ и МСФО.
`SALARY_ACCRUAL`/`SALARY` — уже накопительный, используется как образец.
`DEPRECIATION_ACCRUAL`, `RENT_ACCRUAL` — уже неденежные начисления, не привязаны к оплате, уже корректны.
