## Часть 1 — Критерии готовности

Каждый критерий — это конкретная проверка, не общее описание. Если хотя бы один пункт не выполняется — проект не считается завершённым по плану.

### 1.1 База — план счетов и движок

- В БД сидируется 214 счетов НСБУ №21 (рег. №3593-2), не 24
- Каждый счёт имеет корректный тип: `ASSET / CONTRA_ASSET / LIABILITY / CONTRA_LIABILITY / ACTIVE_PASSIVE / TRANSIT / OFF_BALANCE` — включая явное подтверждение что счёт 6010 типизирован как `ACTIVE_PASSIVE`, не `LIABILITY` (это нужно проверить отдельно, мы это не подтвердили окончательно)
- `postDocument()` отказывает с понятной ошибкой если `accountCode` шаблона не найден в плане счетов — уже работает, не трогать
- Σ Дт = Σ Кт проверяется на каждой проводке — уже работает, не трогать

### 1.2 Каталог типов документов

- Каждый тип из `CONTADOR_DOCUMENT_TYPES_FULL_LIST.md` помечен флагом `BANK_AUTO / MANUAL_ONLY / HYBRID`, и это поле реально используется кодом (не просто документация)
- `GOODS_RECEIVED` и `SERVICE_RECEIVED` реализованы и доступны через ручной ввод
- Старый `SUPPLIER_PAYMENT_GOODS/SERVICES/OTHER` пересмотрен под накопительный метод — проводки идут на 6010 (погашение долга), а не напрямую на 9120/9130/9430
- `FIXED_ASSET_DISPOSAL` создаёт обе обязательные проводки (первоначальная стоимость + износ), не одну
- Счёт 9430 имеет аналитический признак (субконто) по типу документа — штраф отличим от комиссии банка в отчёте

### 1.3 Накопительный метод (Module 1 + зеркальный расходный)

- Поступление от покупателя по умолчанию падает на 6310, не на 9030, если нет подтверждённой ЭСФ
- `INVOICE_CONFIRMED` атомарно закрывает 6310 и признаёт доход + налог одновременно
- `TaxCalendarEvent` создаётся и в момент `INVOICE_CONFIRMED`, и в `finalizePeriod()` — оба пути работают
- На любую промежуточную дату закрытия ОСВ показывает реальный ненулевой остаток на 6310 (неподтверждённые ЭСФ от покупателей) и на 6010 (полученный, но неоплаченный товар) — это главный финальный тест что накопительный метод реально работает, не просто существует в коде

### 1.4 Маркетплейс / эквайринг

- Транзакции от известных контрагентов (Payme и подобные) распознаются автоматически — либо по списку в настройках организации, либо по метке marketplace/Онлайн ККМ в файле soliq
- Полная сумма оборота (включая удержанную комиссию) признаётся только после подтверждения ЭСФ от площадки, не в момент поступления уменьшенной суммы

### 1.5 Каталог + интерфейс выбора (Module 2)

- Поиск по свободному тексту находит тип по синонимам, не только по точному названию — конкретный тест: запрос «ссуда директору» находит `EMPLOYEE_LOAN_ISSUED`
- Группа «Не знаю / другое» видна с первого экрана классификации, не спрятана
- Свободные описания которые не нашли совпадения логируются для еженедельного просмотра

### 1.6 Сверка с soliq (Шаг 6 Wizard)

- Случай «принятая, но не оплаченная ЭСФ» — обязательство признаётся, переносится с месяца на месяц до момента оплаты
- Случай «удержание комиссии» (Payme-тип) — распознаётся отдельно от обычного несовпадения сумм, не считается ошибкой импорта
- Оба случая накапливаются как открытые позиции (`OpenItem`) и не требуют ручного действия пользователя каждый месяц, если ничего не изменилось

### 1.7 Отчёты

- Форма №1 (Баланс): Актив = Пассив + Капитал на любую дату закрытия, включая показ реальной дебиторки/кредиторки
- Форма №2 (P&L): доход и расход в правильном периоде — периоде экономического события, не периоде движения денег
- Cash Flow остаётся кассовым — это не баг, это правильное поведение, не трогать
- Налог к уплате по НДС = исходящий минус входящий, с учётом что обе стороны признаются по накопительному методу (момент получения/подписания ЭСФ), не по моменту денег

## Часть 2 — Флоу пользователя

### Шаг 1 — Загрузка банковской выписки

Без изменений от текущей реализации. Пользователь загружает файл, все платежи и поступления видны.

### Шаг 2 — Уточнение категорий операций

Список всех операций с тем, что назначил классификатор. Для каждой строки пользователь видит человеческое описание (не код), может переназначить вручную через поиск (Module 2) — печатает свободный текст, система предлагает 2-3 наиболее вероятных варианта.

Поступления от покупателей по умолчанию показываются как «Аванс / ожидает подтверждения ЭСФ», не как готовая выручка — это видимое следствие накопительного метода, пользователь видит что система не торопится признавать доход.

Гибридные операции (например платёж поставщику который может оказаться покупкой основного средства) — пользователь может на этом же шаге переклассифицировать в `FIXED_ASSET_PURCHASE`, если это применимо.

### Шаг 3 — Проверка реестра транзакций

Без изменений по структуре: попадает только то, что осталось без категории после Шага 2. Если на Шаге 2 пользователь сам всё разобрал — Шаг 3 пустой.

### Шаг 4 — Начисления периода

Без изменений. Зарплата, амортизация, курсовые разницы — как сейчас.

### Шаг 5

Без изменений.

### Шаг 6 — Сверка с soliq, с двумя доработками

Загружается файл из soliq. Система сопоставляет с уже введёнными операциями.

**Случай «Не сопоставлено: N ЭСФ»** — для каждой несопоставленной ЭСФ пользователь видит: принята ли она (подписана), и есть ли соответствующий платёж в выписке.
- Если принята, платежа нет → создаётся/подтверждается обязательство, переходит в следующий месяц автоматически, без лишнего клика, до момента когда появится платёж
- Если есть и ЭСФ, и платёж, но это уже было обработано на Шаге 2 — soliq просто подтверждает то что уже есть, никакого нового действия

**Случай «Сумма не совпадает» (Payme-тип)** — если контрагент из списка известных площадок, или есть метка marketplace/Онлайн ККМ — система не показывает это как ошибку, а сама создаёт операцию по удержанию комиссии и предлагает подтвердить одним действием.

### Шаг 7 (новый, появляется не каждый месяц) — Подтверждение подписанных ЭСФ

Этот шаг показывается только если есть операции висящие в буфере (6310) дольше обычного, и Шаг 6 ещё не подтвердил их через файл soliq. Список из нескольких строк: «эта оплата уже закрыта счёт-фактурой?» — да/нет по каждой. Если соliq уже подтвердил на Шаге 6 — этот шаг для соответствующих операций не появляется вообще, потому что подтверждение уже произошло автоматически.

Если ничего не висит — шаг невидим, пользователь не замечает его существования, как договаривались в самом начале обсуждения этого механизма.

### Итоговые отчёты

Доступны после прохождения всех шагов — ОСВ, Форма №1, Форма №2, Cash Flow, налоговый календарь с точными суммами и сроками.

## Что подтверждает что план выполнен полностью

Один сквозной тест, не теоретический: организация с отсрочкой платежа (получила товар в марте, оплатила в апреле; продала с НДС, покупатель подписал ЭСФ через месяц после оплаты) проходит весь Wizard от Шага 1 до отчётов, и Форма №2 показывает доход и расход в марте, а не в месяце фактического движения денег — при этом пользователь физически продолжает просто загружать выписку раз в месяц, без понимания происходящей под капотом смены метода учёта.
