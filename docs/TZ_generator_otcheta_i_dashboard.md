# ТЗ: генератор «Расчёта налога на прибыль» + дашборд
**Организация:** GP TECH UNION MCHJ (можно обобщить на любую VAT-организацию Contador)
**Источник структуры форм:** официальные шаблоны my.soliq.uz, отчёт 10205_47 (скрины от 10.07.2026)

---

## Бизнес-задача

**Кто столкнулся с проблемой:** Ahmad — единственный сотрудник и основатель GP TECH UNION, сам ведёт бухгалтерию в Contador и сам подаёт налоговую отчётность на my.soliq.uz каждый квартал/полугодие/год.

**В чём проблема:** «Расчёт налога на прибыль» на my.soliq.uz — это не одна форма, а связка из основной формы и до 11 приложений с жёстко заданной структурой строк и граф (часть приложений — только для квартальной подачи, часть — только для годовой). Чтобы правильно его заполнить, сейчас нужно вручную: поднять нужные проводки в Contador, вручную просуммировать обороты по нужным счетам, вручную разложить суммы по конкретным строкам и графам формы — сверяясь при этом с текстом Налогового кодекса, на который эти строки ссылаются. Это медленно и подвержено ошибкам. Мы это доказали на практике: в ходе аудита GP TECH UNION за апрель-июнь 2026 нашли и исправили несколько системных ошибок именно в этой части учёта (проводки 4310/6010, ошибочное начисление налога с оборота вместо налога на прибыль) — то есть цена ошибки здесь не абстрактная, а уже была реализована один раз.

**Бизнес-цель обновления:** Contador должен сам считать те же самые цифры, которые требует форма my.soliq.uz, в том же разрезе — по тем же кодам строк и тем же графам, что и на портале — и показывать их в собственном интерфейсе в виде «зеркала» формы. Задача пользователя должна свестись к тому, чтобы открыть экран Contador рядом с открытой формой на my.soliq.uz и построчно перенести готовые цифры, а не считать их заново.

**Что явно НЕ входит в эту бизнес-задачу:**
- Автоматическая подача через API my.soliq.uz — отдельный вопрос, не факт что технически возможен (нет подтверждённой информации об открытом API портала).
- Замена бухгалтера/консультанта для сложных случаев (иностранные доходы, дивиденды, постоянные учреждения) — обрабатываются вручную даже после этого апдейта, но структура для них должна существовать в форме.

**Что это даёт бизнесу:**
- Экономия времени на каждую подачу — с часов ручной сверки до минут копирования.
- Снижение риска повторения уже случавшихся ошибок в поданной декларации.
- Побочный эффект — тот же генератор становится потенциальной платной фичой Contador для любого клиента на общем налоговом режиме (НДС + налог на прибыль), не только для GP TECH UNION.

## 0. Область апдейта — делаем ВСЁ приложение сразу, по решению Ahmad

Решение: не откладывать неприменимые сейчас приложения в бэклог, а спроектировать и построить сразу всю форму целиком — просто для GP TECH UNION большинство строк будут рендериться нулями, пока нет соответствующих данных (ОС, экспорта, льгот и т.д.). Так функция сразу «по полочкам» и не потребует доработки архитектуры, когда у компании появятся, например, основные средства.

**Что строим в этом апдейте, полностью:**
- Основная форма «Расчёт налога на прибыль» (строки 010–150)
- Приложение №1 «Совокупный доход»
- Приложение №2 «Расходы (убытки)» — квартальная версия (коды 0101–0137)
- Приложение №2.1 — квартальная детальная версия (коды 0301-0334, если применимо; см. сноску на скрине — фактически это тоже годовая, оставляем нулевой заглушкой с понятным статусом «доступно только в годовом отчёте»)
- Приложения №2.1(а) и №2.1(б) — оба движка себестоимости (прямой и пропорциональный), с рендером нулей для GP TECH UNION, но структурно готовые — понадобятся при годовой отчётности за 2026 год
- №3 (инвестиционный вычет) — 0, нет ОС
- №4 (амортизация) — 0, нет ОС
- №6 (льготы) — рендерится по значению `taxBenefit` из настроек (см. 0.2); для GP TECH UNION = `NONE`, все строки 0
- №7 (нулевая ставка) — 0, не применимо
- №8 (убытки прошлых лет) — считается по историческим данным; если убыток за год останется непокрытым, строка 060 сама заполнится для переноса на 2027 год — то есть логику стоит построить сразу, чтобы за 2027 год ничего не пришлось доделывать вручную
- №9 (спецоперации) — 0
- №10–11 (доходы за пределами РУз, дивиденды) — 0

Каждое приложение в UI должно иметь понятный статус: «Заполнено», «Не применимо (0)», «Требует данных» — чтобы Ahmad с одного взгляда видел, что реально нужно проверить перед подачей, а что просто нулевая заглушка по структуре.

### 0.1 — параметры организации (подтверждено Ahmad)
- `isItParkResident: false` — GP TECH UNION не резидент. Поле в настройках делаем, логику льгот IT Park — заглушкой (см. блок 0.2).
- `costingMethod: 'proportional'` — выбрано и зафиксировано.

### 0.2 — льготы: настройка на уровне организации

В этом апдейте — только поле в настройках (флаг + дата регистрации, см. эпик в разделе 7 ниже, п.1). Для GP TECH UNION значение `NONE`. Полная логика применения льгот по всем налоговым модулям — отдельный эпик, расписан детально в разделе 7.

### 0.3 — метод себестоимости: выбор один раз, смена только между закрытыми годами

Тумблера нет. Организация выбирает метод один раз, дальше ведёт отчётность по нему, пока не закроет год полностью — сменить метод можно только при открытии нового налогового года после полного закрытия предыдущего.

**Модель данных:**

Новая таблица `org_costing_method_history` (а не одно мутируемое поле в настройках — история нужна, потому что генератор годового отчёта за прошлые периоды должен всегда использовать метод, который действовал в ТОМ году, даже если позже организация метод сменила):

| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | |
| `orgId` | fk | |
| `fiscalYear` | int | год, к которому относится метод, напр. `2026` |
| `costingMethod` | enum `'proportional' \| 'direct'` | |
| `setAt` | timestamp | когда зафиксировано |
| `setBy` | fk user | |

**Правила API/бэкенда:**
- Создание записи на `fiscalYear = N` разрешено только если:
  - записи на `fiscalYear = N` ещё нет (первый выбор — свободно, в любой момент года), **или**
  - `fiscalYear = N-1` полностью закрыт (все 4 квартала/12 месяцев закрыты, годовая отчётность подтверждена статусом `CLOSED`) — тогда можно зафиксировать метод на `fiscalYear = N`, включая смену по сравнению с `N-1`.
- Если `fiscalYear = N` уже имеет запись и год ещё не закрыт полностью — попытка создать/изменить запись на этот год должна возвращать ошибку 409 с понятным сообщением («метод фиксируется на весь год, изменить можно только после полного закрытия года»), а не молча перезаписывать.
- Генератор отчёта (основная форма + Приложения №2.1(а)/2.1(б)) при расчёте за конкретный период всегда берёт `costingMethod` из `org_costing_method_history` для соответствующего `fiscalYear`, а не текущее значение настроек — это защищает исторические расчёты от искажения, если метод сменили в будущем.
- Оба движка себестоимости (прямой и пропорциональный) реализуются оба — форма требует Приложение №2.1(а) при прямом методе или №2.1(б) при пропорциональном, в зависимости от того, что зафиксировано за отчётный год; наличие обоих движков не связано с тем, есть тумблер или нет.

### 1.2 Флаг переопределения дефолта — на уровне Document, не JournalEntry

**Исправлено по итогам код-ревью**: изначально в ТЗ поле предлагалось вешать на проводку (`JournalEntry`). Это неверно для архитектуры проекта — проводки генерируются автоматически из `postingTemplate`, пользователь с ними напрямую не работает и не должен. Единица пользовательского ввода в системе — документ/транзакция.

Поле `taxDeductibleOverride: boolean | null` добавляется в таблицу `Document` (или на уровень `StagedTransaction` в момент подтверждения категории пользователем — то, что проще встроить в существующий UI подтверждения категорий). Нужно для случаев, когда один и тот же счёт (например 9430 «прочие операционные расходы») в одном случае вычитаемый, а в другом — нет (штраф vs комиссия банка теперь корректно разносятся по разным типам документов согласно 1.1, но в рамках одного типа документа всё ещё могут быть точечные исключения). Без этого поля маппинг «счёт → строка» не сможет разделить вычитаемое/невычитаемое внутри одного счёта на уровне конкретного документа, не ломая при этом posting engine.

## 2. Основная форма — строки 010–150

Прямые формулы (без пользовательского ввода, всё выводится):

```
010 Совокупный доход всего              = APPENDIX_1.line010
020 Вычитаемые расходы                  = APPENDIX_2.line010.col3 − APPENDIX_2.line010.col4
030 Налогооблагаемая прибыль            = line010 − line020
040 Льготы — всего                      = APPENDIX_6.line030   (0, если MVP без №6)
050 Прибыль по нулевой ставке           = APPENDIX_7.line030   (0, если MVP без №7)
060 Налоговая база                      = max(line030 − line040 − line050, 0)
061 Ускоренная амортизация              = APPENDIX_4 (0, если MVP без №4)
062 Окончательная налоговая база        = line060 − line061
070 Установленная ставка налога, %      = TAX_RATES.PROFIT_TAX (15, если нет льгот/ IT Park)
080 Сумма налога на прибыль — всего     = line062 × line070 / 100
090 Начисленные авансовые платежи       = сумма PROFIT_TAX_ACCRUAL за предыдущие кварталы текущего года
150 К уплате в бюджет                   = line080 − line090  (упрощённо, без строк 100/110/120/130/140,
                                            актуальных только при экспорте/постоянном учреждении — не случай GP TECH UNION)
```

Важно: **line010 и line020 — квартальные (нарастающим итогом с начала года)**, а не за один месяц — то, что мы уже обсуждали в контексте фикса `closing.ts`. Генератор отчёта должен агрегировать за диапазон `[fiscalYearStart, currentQuarterEnd]`, не за один закрытый период.

## 3. Приложение №1 — Совокупный доход

Ключевая строка для GP TECH UNION — **020** «Доход от реализации товаров (услуг)».

| Строка | НСБУ-источник | Комментарий |
|---|---|---|
| 020 | сумма Кт-оборотов 9010/9020/9030 за период (из проводок «ЭСФ подтверждён — зачёт аванса») | это и есть выручка Формы №2, стр.010 — уже проверено на реальных данных, что цифры совпадают |
| 050 | **9530** (тип документа `INTEREST_INCOME_RECEIVED`, `seed-coa.ts:288`) — процентные доходы по вкладам/выданным займам, если есть | сейчас 0 — займ директору выдан без начисления процентов, уточнить с бухгалтером, не нарушает ли это ст. о процентах связанным лицам. **Исправлено по итогам код-ревью**: изначально в ТЗ было ошибочно указано «96xx» — в плане счетов проекта 96xx группа зарезервирована под финансовые расходы (9610 проценты уплаченные, 9620 курсовые убытки), а не доходы; правильный счёт для процентных доходов — 9530. |
| 130 | Кт 9540 (положительные курсовые разницы) | 0, все операции в сумах |
| 090 | безвозмездно полученное имущество | 0 |
| остальные строки (070, 100–288) | не встречались в проводках GP TECH UNION за апрель–июнь | оставить 0, но поля должны существовать |

Строка 010 (итог) = сумма строк 020+050-280 согласно формуле формы, генератор просто суммирует то, что замаплено.

## 5. Дашборд

Отдельная страница (например `/tax-dashboard`), обновляется на лету из проводок, не только на закрытие периода:

**Верхний блок — карточки (текущий квартал, нарастающим итогом с начала года):**
- Совокупный доход
- Вычитаемые расходы
- Налогооблагаемая прибыль (база)
- Расчётный налог по ставке (с пометкой "предварительно" — до подтверждения бухгалтером)
- Уже начислено авансом в этом году
- К доплате / к возврату по итогам квартала

**Средний блок — разбивка расходов по строкам Приложения №2**, таблица: код строки / название / сумма вычитаемая / сумма невычитаемая, с возможностью клика — раскрыть исходные проводки (та же логика "расшифровки", что мы обсуждали для 1С).

**Нижний блок — статус готовности отчёта**: чек-лист по приложениям (какие заполнены/применимы, какие нет, какие требуют ручного подтверждения — например №6, если решится, что GP TECH UNION резидент IT Park).

**Кнопка «Экспорт формы»** — генерирует печатную форму, визуально повторяющую структуру my.soliq.uz (шапка + таблица строк 010–150 + приложения), для сверки перед ручным вводом на портале. Прямая интеграция с API my.soliq.uz — отдельная, более поздняя задача (нужно узнать, есть ли у портала открытый API/формат XML для загрузки, это не факт, что публично документировано).

## 7. Эпик: льготы IT Park Uzbekistan

**Правовая база**: Указ Президента УП-5099 от 30.06.2017, продлён Законом №ЗРУ-1014 от 24.12.2024. Действует для резидентов до 01.01.2028, после этой даты условия льгот меняются (привязка к доле экспорта ≥50% в совокупном доходе и другим критериям) — отдельная, более сложная логика, в этот эпик не входит, будет отдельным эпиком не раньше конца 2027 года.

**Не входит в этот эпик** (нужна валидация юриста/бухгалтера на момент реализации, слишком много нюансов для реализации по общему пересказу закона):
- Дивиденды учредителям-нерезидентам (ставка 5% при экспорте >50%)
- Правила после 01.01.2028
- НДС-агентские обязанности при закупке услуг у нерезидентов сверх освобождения (когда организация выступает налоговым агентом по НДС/налогу на прибыль нерезидента)
- Таможенные льготы на ввозимое оборудование

### 7.1 — Модель данных

Расширить настройки организации:

| Поле | Тип | Описание |
|---|---|---|
| `taxBenefit` | enum `'NONE' \| 'IT_PARK_RESIDENT'` | |
| `itParkResidentSince` | date, nullable | дата регистрации резидентства — льготы применяются только с этой даты вперёд, не задним числом на уже закрытые периоды |
| `itParkCertificateNumber` | string, nullable | номер сертификата резидента, для справки/печати в документах |

Льготы применяются **только к периодам после `itParkResidentSince`**. Если организация получила статус в середине квартала — нужно на уровне бизнес-логики решить, применяется ли льгота с начала квартала или пропорционально (уточнить у бухгалтера при реализации конкретного кейса, не додумывать сейчас).

### 7.2 — Модуль налога на прибыль

- В `closing.ts` (блок E2, тот же, что мы правили для GP TECH UNION) — добавить проверку: `if (org.taxBenefit === 'IT_PARK_RESIDENT' && periodDate >= org.itParkResidentSince) { profitTaxAmt = 0 }`, проводка Дт9810/Кт6410 не создаётся вообще (не 0-суммой, а полностью пропускается — 0-суммовые проводки засоряют журнал).
- В генераторе Приложения №6 «Льготы» (раздел 4 выше, строка 060 «Льготы в виде снижения ставки») — для резидента IT Park вся налогооблагаемая прибыль (строка 020 приложения) попадает в льготируемую сумму, ставка эффективно 0%.
- В основной форме, строка 070 «Установленная ставка налога» — вместо константы `TAX_RATES.PROFIT_TAX` (15%) выводить 0% для резидента.

### 7.3 — Модуль НДС / ЭСФ

Более крупный кусок работы — затрагивает не только закрытие периода, но и сам процесс выставления/подтверждения ЭСФ:
- Организация с `IT_PARK_RESIDENT` не должна начислять исходящий НДС на реализацию IT-услуг (тех видов деятельности, которые попадают под льготу — нужно уточнить полный перечень разрешённых для IT Park видов деятельности, не все виды деятельности резидента обязательно льготируются).
- При закупке IT-услуг у нерезидентов (Google, Facebook, AWS и т.п.) — освобождение от НДС, которое иначе организация платила бы как налоговый агент. Нужна отдельная ветка в модуле учёта импортных услуг.
- Отчёт "Расчёт НДС" (тот, что мы обсуждали строить для видимости НДС в Contador) для резидента IT Park должен показывать нулевые начисления по льготируемым операциям с явной пометкой «льгота IT Park», а не просто нули без объяснения — иначе будет выглядеть как баг, а не как результат льготы.

### 7.4 — Модуль соцналога (проводки ФОТ)

- В логике начисления зарплаты (там же, где сейчас Дт6710 Кт6520 соцналог) — для резидента ставка соцналога 0% вместо 12%. Проводка на счёт 6520 не создаётся или создаётся нулевой (решить по аналогии с 7.2 — вероятно, не создавать вообще).

### 7.5 — Модуль НДФЛ

- Ставка НДФЛ при начислении зарплаты сотрудникам по трудовым договорам — 7,5% вместо 12%. Если в Contador НДФЛ пока не реализован отдельным модулем (не встречалось в проводках GP TECH UNION за апрель-июнь) — фиксируем как отдельную предпосылку: этот пункт эпика блокируется наличием базового модуля НДФЛ, который, возможно, ещё не существует и является отдельной задачей вне рамок даже этого эпика.

### 7.6 — Приёмочные критерии эпика

1. Организация с `taxBenefit = IT_PARK_RESIDENT` и датой регистрации в прошлом при закрытии периода не получает проводку начисления налога на прибыль.
2. Приложение №6 автоматически показывает 100% льготируемой прибыли.
3. НДС по реализации льготируемых видов деятельности не начисляется, отчёт "Расчёт НДС" явно помечает такие операции как льготные, а не просто нулевые.
4. Соцналог по зарплате начисляется по ставке 0%.
5. Организация с `taxBenefit = NONE` (в т.ч. GP TECH UNION) — поведение полностью идентично текущему, ни одна формула не меняется. Регресс-проверка обязательна перед мёржем.
6. Смена `taxBenefit` не пересчитывает задним числом уже закрытые периоды — только с даты, указанной в `itParkResidentSince`, и только для периодов после неё.

### 7.7 — Фазы реализации (если делать не одним куском)

- **Фаза 1** — модель данных (7.1) + модуль налога на прибыль (7.2). Самая изолированная часть, наименьший риск регресса.
- **Фаза 2** — соцналог (7.4), тоже относительно изолирована.
- **Фаза 3** — НДС/ЭСФ (7.3) — самая рискованная часть, затрагивает больше всего существующей логики, делать отдельно с расширенным тестированием.
- **Фаза 4** — НДФЛ (7.5), в зависимости от того, существует ли база для этого модуля.

### 4. Приложения №2.1, №2.1(а), №2.1(б) — годовые версии — уверенность средняя, проверить по факту

Общее у всех трёх: это **только годовая отчётность** — портал показывает явное предупреждение «Ошибка — Данный Расчет заполняется только при представлении налоговой отчетности по итогам года».

**№2.1** — структурно почти дублирует квартальное Приложение №2, но с другой нумерацией кодов: **0301–0334 вместо 0101–0137** (тот же перечень статей расходов — сырьё, топливо, газ, электроэнергия, зарплата+соцналог, амортизация и т.д., в том же порядке). Отличие по существу: строка 020 «Себестоимость реализованных товаров (услуг)» здесь явно расшифрована формулой — **«строка 090 графы 5,7 Приложения 2.1(а) или строка 090 графы 4,6 Приложения 2.1(б)»** — то есть годовая версия явно требует сначала посчитать себестоимость в одном из двух вспомогательных приложений (в зависимости от выбранного метода), а квартальная версия такой явной ссылки на дочерний расчёт не показывает.

**№2.1(а)** («по статьям прямых затрат», используется при прямом методе) и **№2.1(б)** («по сумме прямых затрат», используется при пропорциональном методе) — это подробный расчёт себестоимости с движением незавершённого производства (НЗП) и готовой продукции: строки 010 (НЗП на начало периода), 020 (расходы на производство за период, с детализацией сырьё/зарплата/амортизация/прочее по-под-строкам), 030 (всего затрат), 031 (корректировки затрат), 040 (остаток НЗП на конец), 050 (готовая продукция на начало), 060 (поступление готовой продукции за период), 070 (всего готовой продукции), 080 (остаток на конец), 090 (итоговая себестоимость реализованного — эта строка и есть источник для строки 020 Приложения №2.1). Колонки различаются между (а) и (б): в 2.1(а) для «Налоговый учёт – пропорциональный метод» есть дополнительная графа «коэффициент налогового учёта», которой нет в 2.1(б).

**Важно — на портале есть встроенная кросс-проверка:** внизу форм 2.1(а)/2.1(б) отображается предупреждение «Ошибка — Для расчета налога следует заполнить исходя из выбранного метода определения себестоимости товаров (услуг)» — то есть портал сверяет, что заполнено именно то приложение (а) или (б), которое соответствует методу, отмеченному в шапке основной формы. Contador должен воспроизводить эту же логику: если `costingMethod = proportional`, генерируется и заполняется №2.1(б), а №2.1(а) остаётся пустой заглушкой (и наоборот).

**Точную вложенную структуру под-строк 0101-0104/0201-0204/0301-0304 и т.д. внутри 2.1(а) и 2.1(б) нужно сверить по фактическим файлам скриншотов**, которые Ahmad прикрепит к этому документу — на уровне «есть такие строки, в целом такой порядок» я уверен, но точное присутствие/отсутствие определённых под-строк в каждой из двух версий по памяти не гарантирую.
