# Модуль E — Закрытие месяца

**Статус:** Локальная транзакционная защита; полная бухгалтерская приёмка не пройдена
**Файлы:** `src/app/closing/`, `src/app/api/closing/`, `src/lib/closing.ts`  
**Последнее обновление:** 2026-09-10

---

## Назначение

7-шаговый мастер для полного закрытия учётного периода: импорт выписки → классификация → реестр → начисления → курсовые разницы → Soliq → финализация.

---

## Архитектура мастера

**Компонент:** `ClosingWizard.tsx` — контейнер, управляет состоянием шагов.  
**Состояние:** `ClosingJob.data/step`; прежний `Period.closingData` используется как fallback при отсутствии задания. Глобального in-memory кэша нет.

Контейнер пересоздаётся при смене periodId: до успешной загрузки нового периода
старые формы/суммы не показываются. Начальная загрузка проверяет HTTP и форму
ответов state, pending-invoices и dashboard; ошибка даёт отказ с повтором,
не пустые данные. Чтения ограничены 30 секундами и отменяются при размонтировании.
Переход проверяет ЭСФ и остаётся на текущем шаге при ошибке; параллельные
переходы не запускаются. Поздние ответы старого периода игнорируются.

### Транзакционный контракт

- `finalizePeriod` блокирует принадлежащий организации Period (`FOR NO KEY UPDATE`) до чтения задания и начислений. Строки банка IMPORTED/NEEDS_CLARIFICATION запрещают закрытие.
- Начисления, календарь, реформация, COMPLETED, блокировка месяца и аудит CLOSE_PERIOD входят в одну транзакцию (maxWait 5 с, timeout 30 с). Ошибка откатывает всё, включая RUNNING; отдельная запись FAILED после отката больше не создаётся. Существующие старые RUNNING требуют отдельной диагностики.
- Повтор для CLOSED + COMPLETED возвращает период без повторных начислений и аудита. Прямой API `periods/[id]/close` вызывает этот же сервис, проверяет текущую роль и запрещает `force`.
- Оба API закрытия требуют актуальную роль OWNER/ADMIN/ACCOUNTANT и используют пользователя/организацию из членства. Чужой период даёт 404. Строгий JSON допускает только boolean `confirmMissingCogs` у `closing/[periodId]/finalize` либо boolean `force` у прямого close; пустое тело допустимо, повреждённые/лишние параметры дают 400. Финализация возвращает PostingValidationError как 400, MissingCogsError как 409 с кодом MISSING_COGS.
- Чтение/сохранение мастера проверяет orgId и блокирует период; запись в закрытый/заблокированный месяц запрещена.
- Reopen блокирует периоды организации в хронологическом порядке, запрещён при последующих CLOSED, в том числе следующего года. Сброс ClosingJob, открытие месяца и аудит атомарны. Поздние налоговые начисления удаляются только из OPEN месяцев того же года; прежние закрытые месяцы не изменяются.
- Переоткрытие восстанавливает долги, погашенные системными документами (включая SALARY_OFFSET), вместо удаления этих долгов. Внешнее погашение долга, открытого системным документом, блокирует переоткрытие. Неизменяемые версии/сторно не реализованы; системные документы по-прежнему удаляются. Декабрь с YEAR_END_CLOSE по-прежнему заблокирован для reopen.
- Отдельный API годового переноса проверяет текущую роль OWNER/ADMIN/ACCOUNTANT. В одной транзакции сначала блокирует Period, затем advisory lock YEAR_END_CLOSE, проверяет CLOSED/декабрь/дубликат и создаёт перенос с аудитом реального пользователя. Годовая выборка использует границы Asia/Tashkent, документ датируется последней миллисекундой года. Прибыль: Дт 9910 / Кт 8710; убыток: Дт 8710 / Кт 9910. Общие документные API запрещают YEAR_END_CLOSE.
- Годовой статус возвращает done=true только для POSTED YEAR_END_CLOSE в своём закрытом декабре. Нет periodId: 400; чужой/неизвестный период: 404; отозванное членство: 403. DRAFT/VOIDED не подтверждают перенос; POST при таком дубликате отвечает 409 YEAR_END_REQUIRES_REVIEW без записей. Это проверка состояния, не независимая сверка его проводок.
- Банковский импорт блокирует счёт, затем периоды в порядке дат; строки, остаток и IMPORT_BANK фиксируются вместе. Движение суммируется BigInt в сотых. Закрытые строки пропускаются с `locked`, остальные загружаются атомарно. Новый hash bank-v2 включает организацию, счёт, валюту, дату, направление, сумму с двумя знаками и назначение. Старый hash признаётся дублем только после сверки сохранённых полей, включая направление; исторические hash не переписываются. Парсер 1С сохраняет точные строковые суммы; Number используется только для совместимого legacy-хеша. Банковский reference, полноценный реестр партий и проверка непрерывности не реализованы.

Техническая реформация PERIOD_CLOSING датируется последней миллисекундой месяца
по Asia/Tashkent, автоматический декабрьский YEAR_END_CLOSE использует ту же
границу. Начисления пока остаются на 28-м числе, но уже в явном часовом поясе;
политика даты первички не решена. Накопленная бухгалтерская прибыль и месячная
база налога с оборота учитывают обе стороны счетов, включая обратные проводки.
Это не единая нормативно утверждённая налоговая база.

Это не подтверждает правильность налоговой базы, валютной оценки и всех источников записи. Проверены синтетические транзакции на одноразовом PostgreSQL, без production-данных.

### Удаление периода

`DELETE /api/periods/[id]` допускается только с актуальным членством OWNER/ADMIN
и только для пустого OPEN периода без lockDate. ACCOUNTANT/VIEWER получают 403,
чужой или неизвестный период 404, закрытый/заблокированный 400. Документы любого
статуса, строки банка, налоговые события, любой ClosingJob, любой SoliqImportBatch,
любое closingData кроме null, ссылки correctionForPeriodId/affectedPeriodId своей
организации дают 409 PERIOD_NOT_EMPTY. Даже DRAFT-задание, созданное чтением
мастера, сохраняется. Отдельного удаления или очистки дочерних записей нет.

Period блокируется FOR UPDATE до проверки связей: это препятствует новым
FK-ссылкам во время удаления. Удаление пустого периода и DELETE_PERIOD с
текущим пользователем/метаданными выполняются в одной транзакции
(maxWait 5 с, timeout 10 с); сбой аудита откатывает удаление. Подтверждение
в интерфейсе больше не обещает стереть учётные данные.

Проверены роли, tenant, сохранность долга из прошлого месяца и его проводок,
VOIDED-документов, банковских строк, календаря, заданий и всех трёх статусов
Soliq. SQL-тесты проверяют rollback, два конкурентных DELETE и FK lock timeout
конкурентного создания документа. Это не гарантия против прямого SQL DELETE,
каскада удаления организации или новых несогласованных записей строковых
ссылок без FK. Архивирование/неизменяемые версии остаются отдельными задачами;
схема БД на этом этапе не менялась. Ограниченный rollback банка описан ниже.

### saveClosingState

```typescript
async function saveClosingState(periodId: string, patch: any, orgId?: string, transaction?: Prisma.TransactionClient): Promise<void>
```

- Выполняет мелкое слияние `patch` в `ClosingJob.data`, используя legacy `closingData` при отсутствии задания.
- `orgId` обязателен; принадлежность и блокировка периода проверяются внутри транзакции.
- Обновляет `ClosingJob` в БД; во время RUNNING или после закрытия сохранение запрещено.
- Использует переданную транзакцию либо открывает собственную; импорт Soliq передаёт свою, чтобы ошибка прогресса откатывала также проводки и зачёты.

## Шаги мастера (7 шагов)

### Шаг 1 — Импорт выписки (`Step1Import.tsx`)

- Выбор банковского счёта + загрузка файла
- Формат: 1CClientBankExchange (.txt, UTF-8/CP1251), непустой файл до 5 МиБ.
  Excel/неизвестные форматы временно запрещены API (422 BANK_STATEMENT_UNSUPPORTED).
- API поддерживает preview без записей с точными строковыми суммами; Step1
  загружает файл непосредственно, без предварительного preview.
- Один 20-значный счёт выписки должен совпасть с BankAccount до preview и под
  lock. Обязательны период и оба контрольных остатка; невозможные даты,
  неоднозначное направление, повторные поля и нестрогие суммы отклоняются.
- Равенство начального остатка и движений конечному проверяется в сотых до
  транзакции. При новых строках несовпадение конечного остатка с состоянием банка
  даёт 422 BANK_STATEMENT_INVALID и полный откат, а не предупреждение после записи.
- Валюта, непрерывность и уникальность номера в БД пока не подтверждаются.
  Лимит file.size действует после разбора multipart, не ограничивает всё HTTP-тело.
- BankAccount POST/PUT/DELETE разрешены OWNER/ADMIN и атомарны с аудитом.
  POST требует 20-значный номер; POST/PUT сериализуют проверку нормализованных
  дубликатов в организации. Финансовые реквизиты счёта с импортной историей
  неизменяемы через PUT; удаляется только пустой нулевой счёт без истории.
  После отката импорта запрет сохраняется. Это API-защита, не DB UNIQUE.
- Импорт → `StagedTransaction[]` со статусом `IMPORTED`
- Кнопка «Откатить» вызывает `DELETE /api/import/bank/rollback` с UUID batchId.
  Только OWNER/ADMIN могут отменить неизменённую необработанную партию одного
  счёта в открытых незаблокированных периодах. Отсутствие снимка, последующий
  аудит/изменение счёта, документы или обработка строк дают отказ без записей.
- Новый импорт хранит в IMPORT_BANK снимки остатка/синхронизации/валюты/номера
  счёта до и после, rollbackVersion=2, число строк и SHA-256 исходных полей. Откат проверяет
  эти сведения под блокировками банка, периодов и строк. Удаление проверенных
  строк, точное восстановление прежнего состояния и ROLLBACK_IMPORT_BANK с
  копиями строк/актором атомарны (maxWait 5 с, timeout 15 с).
- Старые партии без снимка версии 2 с номером счёта требуют сверки. После отката последнего импорта
  предыдущий не откатывается автоматически. AuditLog пока изменяем на уровне
  SQL, исходный файл банка не сохраняется: это не полный неизменяемый регистр.

### Шаг 2 — Классификация (`Step2Clarification.tsx`)

- Запускает движок правил → AI-классификатор (GPT-4o-mini)
- Показывает очередь NEEDS_CLARIFICATION групп
- При ответе на все → переход к шагу 3
- Опция «запомнить» — создаёт новое правило

### Шаг 3 — Реестр документов (`Step3Registry.tsx`)

Показывает **все** транзакции периода — и нераспознанные, и те что классифицировал AI — для проверки и ручной корректировки.

**Запрос:** `GET /v2/api/transactions?periodId=...&status=IMPORTED,NEEDS_CLARIFICATION,AUTO_MATCHED&limit=2000`

**Сортировка:** нераспознанные (`IMPORTED`, `NEEDS_CLARIFICATION`) выводятся первыми, затем AI-распознанные.

**Фильтр-вкладки (клиентская фильтрация):**

| Вкладка | Отображаемые статусы |
|---------|---------------------|
| Все (N) | IMPORTED + NEEDS_CLARIFICATION + AUTO_MATCHED |
| Без категории (N) | IMPORTED + NEEDS_CLARIFICATION |
| Распознано ИИ (N) | AUTO_MATCHED |

**Поведение колонки «Категория»:**

- `IMPORTED` / `NEEDS_CLARIFICATION`: всегда показывает `<select>` с кнопкой ✓
- `AUTO_MATCHED` / `CONFIRMED`: показывает название текущей категории; при наведении — иконка карандаша; клик → `<select>` с предвыбранной категорией + кнопки ✓ и ×

**Статусные бейджи:**

| Значение | Бейдж |
|---------|-------|
| IMPORTED | `Новый` (серый) |
| NEEDS_CLARIFICATION | `Не распознан` (красный) |
| AUTO_MATCHED | `ИИ` (синий) |
| CONFIRMED | `✓` (зелёный) |

После ручного изменения категории через `PATCH /api/transactions/[id]/category` транзакция **обновляется в месте** (не удаляется из списка) — пользователь сразу видит новое значение.

Кнопка «Продолжить» отображает счётчик оставшихся без категории: `Продолжить (5 без категории) →`.

### Шаг 4 — Начисления (`Step4Accruals.tsx`)

Ввод сумм, отсутствующих в выписке. Данные и номер следующего шага сохраняются
одним вызовом `saveClosingState` в `ClosingJob.data.accruals` с блокировкой периода.
`closingInput.ts` используется формой, API и `finalizePeriod`: обязательные
неотрицательные суммы, максимум две значащие дробные цифры, запрет пустоты,
экспонентных строк, мусора, неизвестных полей и потери точности при Number.
Форма отправляет исходные десятичные строки. Совместимость числового состояния
пока сохранена: это не общая decimal-политика. Некорректный legacy/ClosingJob/
override блокирует закрытие до RUNNING и начислений, без исправления истории.
Для положительного ФОТ обязательна функция сотрудника (9110/9410/9420/9430);
таблица ниже показывает административную функцию 9420.

API состояния возвращает сохранённые суммы без подстановки начислений прошлого
месяца: явный ноль, сброс и десятичные строки сохраняются. Автоматический перенос
старых сумм отключён, новые начисления нужно подтвердить вводом. Метаданные
периода берутся из tenant-проверенной записи, не из произвольного поля состояния.
Форма пересоздаётся по periodId, отменяет старый GET подсказок и игнорирует
поздние POST/DELETE. Сброс и сохранение взаимно блокируют кнопки; ошибка
сохраняет ввод для повтора. Игнорирование ответа не отменяет серверную запись.

| Поле | Тип документа | Проводка |
|------|-------------|---------|
| ФОТ | SALARY_ACCRUAL | Дт 9420 → Кт 6710 (брутто) |
| | | Дт 6710 → Кт 6530 (ИНПС 0.1%) |
| | | Дт 6710 → Кт 6410 (НДФЛ в бюджет 11.9%) |
| | | Дт 9420 → Кт 6520 (соцналог 12%) |
| Амортизация | DEPRECIATION_ACCRUAL | Дт 9430 → Кт 0200 |
| Аренда | RENT_ACCRUAL | Дт 9420 → Кт 6010 |

**API:**
```
POST /api/closing/[periodId]/step/4/complete
Body: { salaryAmount, depreciationAmount, rentAmount, expenseAccountCode }

DELETE /api/closing/[periodId]/accruals
→ { reset: true }
```

### Шаг 5 — Курсовые разницы (`Step5FxDiff.tsx`)

- Ручной ввод курса; `GET /api/cbu-rate` загружает текущий курс, не подтверждённый исторический курс конца периода.
- Общая строгая схема требует неотрицательный курс и денежную разницу со знаком;
  ненулевая разница без положительного курса запрещена. Сохранение данных/
  прогресса атомарно. Только после успешной проверки отсутствия иностранных
  банковских счетов форма сохраняет нули через API и после успеха переходит
  дальше. Это не проверка валютной задолженности.
- Любой банковский счёт своей организации с валютой кроме UZS/USD блокирует
  форму, сохранение fxDiff и финализацию до записей, даже с нулевым остатком.
  Сервер проверяет и legacy-состояние, и ClosingJob. Чужие счета не блокируют.
- Ошибка банковского API или некорректные данные дают видимый отказ и повтор,
  не нулевую разницу. При смене периода форма пересоздаётся; поздние ответы
  старого периода не изменяют новый экран и не вызывают переход мастера.
- Расчёт: (текущий курс − предыдущий) × остаток счёта 5210
- Если разница ≠ 0 → документ `FX_DIFFERENCE` с payload `{ fxDifference, fxAccountCode: "5210" }`:
  - Доход: Дт $fxAccountCode → **Кт 9540** (FX_INCOME)
  - Расход: Дт **9620** → Кт $fxAccountCode (FX_EXPENSE)

Счета 9540 и 9620 (не 9030/9430) — из констант `ACCOUNTS.FX_INCOME` / `ACCOUNTS.FX_EXPENSE`.
`$fxAccountCode` — счёт из payload, а не хардкод в шаблоне; этот автоматический шаг мастера
всегда передаёт `"5210"` (валютный банковский счёт). Переоценка других валютных статей
(4010, 4310, 6010, 6820 в валюте) через FX_DIFFERENCE выполняется отдельно, вручную, через
«Документы → Создать документ» с нужным `fxAccountCode` — движок не хранит валюту по
OpenItem/проводке, поэтому не может пересчитать их автоматически.
Расчёт формы всё ещё ограничен USD. Защита использует текущую валюту BankAccount,
не историю периода; конкурентное создание/изменение валюты счёта не сериализовано
с закрытием. Это временный отказ для неподдерживаемых счетов, не валютный регистр.
Достоверность курса, полнота денежных статей и расчёт по НСБУ №22 не подтверждены.

### Шаг 6 — Soliq (`Step6Soliq.tsx`)

Локальная реализация 2026-09-10, без выпуска:

- `POST /v2/api/import/soliq` принимает файл до 5 MiB и период. Все строки должны
  относиться к этому месяцу в Asia/Tashkent; неверная дата не заменяется текущей.
  Нужны распознанный шаблон, ИНН 9/14 цифр и корректные суммы с максимум двумя
  знаками. Максимум 2000 строк; gross ограничен безопасным целым числом сотых.
- В `SoliqImportBatch` сохраняются оригинальные байты, SHA-256, версия парсера,
  строки со стабильным `rowId`, денежные строки fixed-2, итоги и автор.
  Повторная загрузка того же READY возвращает сохранённые данные. Проведённый
  импорт периода запрещает новую загрузку, отменённый файл нельзя загрузить заново.
- `GET /v2/api/import/soliq?periodId=...` возвращает READY и признак `imported`;
  дополнительный `batchId` восстанавливает предпросмотр с проверкой источника/итогов.
  Чтение не создаёт ClosingJob. После возврата к проведённому шагу «Продолжить»
  только переключает экран и не отправляет skip/повторное проведение.
- Архив POSTED/CANCELLED доступен из того же шага. Ссылки
  `GET /v2/api/import/soliq/[batchId]/export?format=source|protocol` выгружают
  исходные байты или JSON с метаданными/строками/итогами/результатом. Требуются
  текущее членство, совпадение организации batch/периода и SHA-256. Закрытый
  период доступен для чтения; ответы attachment/no-store/nosniff не меняют БД.
  При смене периода UI пересоздаётся; запоздалый ответ старого шага не вызывает
  переход мастера в новом периоде.

#### Сопоставление и проведение

Автоматически выбирается только единственный точный аванс своей организации:
ИНН, gross, счёт 6310 (REVENUE) или 4310 (EXPENSE), OPEN/RISK без погашения,
проведённый источник и допустимая дата. Авансы прошлых месяцев допустимы,
будущие относительно ЭСФ исключены. Один аванс не выбирается дважды.
Нечёткое совпадение названий и допуски суммы не разрешают автоматический зачёт.
Ручной/опциональный AI-выбор меняет решение по `rowId`, не финансовые данные.

`POST /api/closing/[periodId]/step/6/complete` принимает только
`{batchId, decisions: [{rowId, openItemId, receiptKind?}]}`. Для каждой строки
нужно ровно одно решение; `openItemId: null` означает отсутствие зачёта.
Клиентские суммы, НДС, направление, дата и `parsedPayload` не принимаются.
`receiptKind` выбирает товары/услуги; при отсутствии применяется существующая
логика `receiptKind.ts` по платежу, для продажи по умолчанию услуги.

Свежая роль OWNER/ADMIN/ACCOUNTANT обязательна. Одна транзакция (ожидание 5 с,
таймаут 120 с) блокирует Period FOR NO KEY UPDATE и batch FOR UPDATE,
перепроверяет OPEN/lockDate, источник/версию/строки/итоги и выбранные авансы.
Маркер, документы, точные зачёты, аудит, ClosingJob и итоговый статус POSTED
сохраняются атомарно. Выбранный openItemId не заменяется другим равным долгом.
Банковский зачёт без регистра использования и комиссия из разницы запрещены.

Перед фиксацией повторно читаются документы и JournalEntry: проверяются число,
ссылки batch/row, суммы и независимая корреспонденция `soliqLedger.ts` для восьми
типов товаров/услуг с авансом/без. Выручка отделяется от НДС 6410, приобретение
от НДС 4410; просто сбалансированных, но неверных проводок недостаточно.
Протокол содержит markerId, документы/типы по rowId, решения, итоги и
`ledgerControl.version = soliq-v1`. Пустой реестр тоже проводится как batch,
с маркером и нулевым протоколом, но без проводок.

#### Отмена и ограничения

`POST /v2/api/import/soliq/[batchId]/discard` принимает непустую причину,
переводит READY в CANCELLED под блокировкой открытого периода, сохраняет автора
и время. Оригинал остаётся. READY блокирует финальное закрытие; дополнительные
READY после проведения другого пакета требуют явной отмены.
`{skip:true}` допустим только без READY/POSTED и старого маркера SOLIQ_IMPORT.

Сырые SQL-ограничения/триггер из `prisma/migrations/20260910_soliq_import_batch.sql`
обязательны: Prisma db push их не устанавливает. Источник неизменяем, POSTED и
CANCELLED нельзя обновлять. Защита от DELETE/каскада пока отсутствует.
Нет полной защиты распаковки XLSX, регистра валютных
распределений и двойного признания между источниками. Проверка проводок не
подтверждает право на вычет НДС или налоговую методику. ACC-005/006 и ворота
TASK-0005 не считаются полностью принятыми.

### Шаг 7 — Финализация (`Step7Summary.tsx`)

**Вызов:** `POST /api/closing/[periodId]/finalize`

Вся финализация выполняется в **одном** `prisma.$transaction()`.

UI проверяет успешность и схему сводки/годового статуса. При ошибке или таймауте
30 секунд закрытие недоступно, показан повтор; нулевые KPI не подставляются.
При смене периода сбрасываются сводка, диалог и результат. Успешный finalize
принимается только с ID выбранного периода и статусом CLOSED; поздний ответ
старого периода не вызывает onFinalized. Годовой POST 409 считается уже
выполненным только после отдельного успешного GET с done=true.
POST-запросы самого Step7 пока не имеют клиентского таймаута; серверная
транзакция ограничена временем. Проверки jsdom не заменяют визуальные/auth E2E.

## Алгоритм finalizePeriod() (`src/lib/closing.ts`)

### Блок A — Начисление зарплаты

- Создаёт SALARY_ACCRUAL если `salaryAmount > 0` и документ ещё не существует
- Шаблон генерируется через upsert (обновляет ставки при изменении)
- Дополнительно: если у сотрудников есть займ (сальдо 4720 > 0) → создаёт SALARY_OFFSET на нетто-зарплату (коэффициент 1 − NDFL = 0.88)

### Блок B — Амортизация

- Создаёт DEPRECIATION_ACCRUAL если `depreciationAmount > 0`
- Проводка: Дт 9430 → Кт 0200

### Блок C — Аренда

- Создаёт RENT_ACCRUAL если `rentAmount > 0`
- Проводка: Дт 9420 → Кт 6010

### Блок D — Курсовые разницы

- Создаёт FX_DIFFERENCE если `fxDiff.difference ≠ 0`
- Использует условные строки (condition) в шаблоне

### Блок E — Налоги

Агрегирует JournalEntry за период для расчёта выручки и прибыли:
- `totalRevenue` = Кт(9010 + 9020 + 9030) за период
- `otherIncome` = Кт − Дт по счетам 93xx
- `netProfit` = выручка + прочие доходы + fx-доходы − все расходы − fx-расходы

**Режим VAT — налог на прибыль (квартальный, нарастающим итогом):**
- Начисление только при закрытии квартальных месяцев (3/6/9/12) — отчётный период
  по налогу на прибыль — квартал (ст. 338 НК), база — нарастающим итогом с начала
  года (ст. 296 ч.4, ст. 339 ч.2 НК).
- Формула: `delta = max(кумулятивная прибыль года, 0) × org.profitTaxRate − уже
  начисленное за год`. Кумулятивная прибыль считается `computeCumulativeNetProfit`
  (та же формула, что месячный netProfit, но по диапазону дат с 1 января,
  документы PERIOD_CLOSING исключены).
- `delta > 0` → `PROFIT_TAX_ACCRUAL` (Дт 9810 → Кт 6410);
  `delta < 0` (кумулятив упал после убыточного квартала) → `PROFIT_TAX_REVERSAL`
  (Дт 6410 → Кт 9810). Payload обоих: `{ taxAmount, year, quarter, cumulativeBase,
  cumulativeTaxDue, accruedBefore }`.
- Ставка — `org.profitTaxRate` (дефолт 0.15; ст. 337 НК: банки/мобильная связь 20%,
  отдельные категории 0%).
- Проводки создаются только при `org.autoAccrueProfitTax = true` (дефолт). При
  `false` организация считает налог вручную; событие PROFIT_TAX в календаре
  создаётся всегда (в квартальные месяцы, в т.ч. с суммой 0 — фиксирует расчёт).
- Срок события: 20-е число месяца после квартала (ст. 339 ч.5 п.1); для Q4 —
  1 марта следующего года (ст. 339 ч.5 п.2). Сумма события `max(delta, 0)` —
  к доплате не бывает отрицательной (ст. 340 ч.7).
- Перенос убытков прошлых лет (ст. 333 ч.6) в квартальных расчётах не применяется —
  только в годовом расчёте (Фаза 2); убыточные месяцы текущего года поглощаются
  нарастающим итогом автоматически.
- **Reopen:** сначала необходимо переоткрыть последующие закрытые месяцы.
  Удаляются системные документы текущего месяца и PROFIT_TAX_ACCRUAL/REVERSAL
  более поздних OPEN месяцев того же года. Закрытые месяцы не переписываются.

**Режим TURNOVER_TAX:**
- Если `totalRevenue > 0` → `TURNOVER_TAX_ACCRUAL` (Дт 9810 → Кт 6410)
- Ставка: `org.turnoverTaxRate` (дефолт 4%)

### Блок F — Налоговый календарь

Удаляет старые PENDING-события периода, затем создаёт новые `TaxCalendarEvent`:
- PERSONAL_INCOME_TAX (НДФЛ 11.9% от ФОТ)
- INPS (0.1% от ФОТ)
- SOCIAL_TAX (12% от ФОТ)
- PROFIT_TAX или TURNOVER_TAX (в зависимости от режима)

Срок: 20-е число следующего месяца (`CLOSING.TAX_DUE_DAY = 20`).

### Блок G — Динамический пересчёт налогового календаря

После создания событий вызывает `upsertTaxCalendarEventsForPeriod(periodId, orgId, tx)`:
- Для режима VAT: рассчитывает НДС = исходящий НДС (6410, кроме налоговых начислений) − входящий НДС (4410)
- Для режима TURNOVER_TAX: пересчитывает налог с оборота по актуальной выручке
- Создаёт или обновляет `TaxCalendarEvent` типа VAT / TURNOVER_TAX

Ошибка `upsertTaxCalendarEventsForPeriod` прерывает проведение и откатывает транзакцию.

### Блок H0 — Предупреждение по счетам выбытия активов

Перед реформацией проверяет чистый оборот TRANSIT-счетов 9210 (Выбытие ОС) и 9220 (Выбытие
прочих активов): если ненулевой — значит `FIXED_ASSET_DISPOSAL` был проведён, но
`FIXED_ASSET_DISPOSAL_RESULT` (признание прибыли/убытка) не создан для всех выбытий периода.
Ненулевой остаток блокирует закрытие и откатывает транзакцию.

### Блок H — Реформация баланса (PERIOD_CLOSING)

Переносит ненулевые TRANSIT-счета (9xxx) на 9910:
```
Кредитовый остаток (доходный счёт):  Дт 9xxx → Кт 9910
Дебетовый остаток (расходный счёт):  Дт 9910 → Кт 9xxx
```

Один документ `PERIOD_CLOSING` на весь период.

### H2 — Годовое закрытие при декабре

Если `period.month === 12` — автоматически выполняет перенос 9910 → 8710 внутри той же транзакции (если документ YEAR_END_CLOSE ещё не существует).

### Блок I — Блокировка

`Period.status = "CLOSED"`, `Period.lockDate = последний день месяца`.

## Годовое закрытие (Year-End Close)

**Файл:** `src/app/api/closing/year-end/route.ts`  
**Условия:** декабрь + период CLOSED + нет дублирующего YEAR_END_CLOSE

**Вызов:**
```
POST /api/closing/year-end
Body: { periodId }
```

**Алгоритм:**
1. Проверить: период декабря, CLOSED, без дубля
2. Вычислить `net9910 = Σ(credit − debit)` по счёту 9910 за весь год (raw SQL). Знак изменён
   на интуитивный (было `Σ(debit − credit)` с прибылью при `< 0`, что уже приводило к ошибке
   реализации) — теперь прибыль соответствует `net9910 > 0`, согласовано между
   `src/lib/closing.ts` (H2, автоматически при закрытии декабря) и `src/app/api/closing/year-end/route.ts` (этот ручной запуск).
3. Если `net9910 = 0` → возвращает `{ transferred: 0 }` без создания документа
4. Создать документ `YEAR_END_CLOSE` (дата: 31 декабря)
5. Проводки в `prisma.$transaction()`:
   - Прибыль (`net9910 > 0`, кредитовый остаток): **Дт 9910 → Кт 8710**
   - Убыток (`net9910 < 0`, дебетовый остаток): **Дт 8710 → Кт 9910**
6. Записать `AuditLog` (action: `YEAR_END_CLOSE`, userId: `"system"`)

**Результат:** `9910 = 0`, `8710` = накопленная нераспределённая прибыль.

## Переоткрытие периода

**API:** `POST /api/periods/[id]/reopen`

Требует: период закрыт, нет документа YEAR_END_TRANSFER в следующем году.

В `prisma.$transaction()`:
1. Найти и удалить системные документы закрытия (PERIOD_CLOSING, SALARY_ACCRUAL, DEPRECIATION_ACCRUAL, RENT_ACCRUAL, FX_DIFFERENCE, PROFIT_TAX_ACCRUAL)
2. Удалить связанные OpenItem
3. Удалить PENDING TaxCalendarEvent периода
4. Разблокировать: `status = "OPEN"`, `lockDate = null`, `closingData = DbNull`

Затем сбрасывает in-memory кэш: `clearClosingState(id)`.

## Режимы периода (Period.mode)

Поле `mode` в таблице `Period` существует в схеме БД, но с 2026-07-01 **активно используется только одно значение — `ACTIVE`**.

| Значение | Статус | Описание |
|---------|--------|---------|
| `ACTIVE` | ✅ Используется | Полный 7-шаговый wizard |
| `HISTORICAL` | ❌ Удалён из UI | Упрощённый режим (только импорт + закрытие) — удалён |

**Что изменилось:**
- Форма создания периода больше не показывает выбор типа — всегда создаётся `ACTIVE`
- При автоматическом создании периода из банковского импорта (`import/bank/route.ts`) — всегда `ACTIVE`, ранее прошедшие периоды получали `HISTORICAL`
- Существующие периоды с `mode=HISTORICAL` в БД открываются в полном `ClosingWizard`
- Компонент `Step1Import` больше не рендерится в `page.tsx` напрямую — только внутри wizard'а

- Период нельзя закрыть повторно (`Period.status === "CLOSED"` → 409)

- Вся финализация в одном `prisma.$transaction()`
