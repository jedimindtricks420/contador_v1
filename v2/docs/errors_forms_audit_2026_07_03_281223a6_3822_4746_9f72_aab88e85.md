## 1) Критическая ошибка: `TURNOVER_TAX` отражается через `9820` вместо `9810`

### Где найдено

**Шаблон документа:**
- `v2/src/lib/ensureBaseData.ts:432-439`

```ts
code: "TURNOVER_TAX_ACCRUAL",
...
{ accountCode: "9820", side: "debit", expression: "taxAmount" },
{ accountCode: "6410", side: "credit", expression: "taxAmount" }
```

**Логика закрытия периода:**
- `v2/src/lib/closing.ts:251`

Комментарий в коде:
```ts
// E3. Налог с оборота: проводка Дт 9820 — Кт 6410
```

### Почему это ошибка

По документации и спецификации для налога с оборота ожидается отражение через **`9810`**, а не через `9820`.

Это подтверждается ранее прочитанными материалами проекта:
- `README.md`
- `docs/update_v1.md`
- `docs/contador_accounting_engine_spec.md`
- `v2/docs/modules/module_G_reports.md`

### Влияние

Это критично для **Формы №2**:
- строка **250** должна отражать налог, который идёт через `9810`
- строка **260** относится к `9820`

Если налог с оборота уходит в `9820`, то:
- строка **250** будет неверной
- строка **260** будет содержать данные не по назначению
- строка **270** (чистая прибыль/убыток периода) может считаться неверно

Также это влияет на **Форму №1**:
- строка **450** (нераспределённая прибыль) может быть искажена после закрытия периода

### Приоритет

**Критический. Исправлять в первую очередь.**

## 2) Ошибка балансового контроля в Form 1

### Где найдено

- `v2/src/app/api/reports/balance/route.ts:199`

```ts
const balanceOk = line400.equals(line780);
```

### Почему это ошибка

В документации проекта для балансового контроля указан допуск:

```ts
line400.minus(line780).abs().lte(1)
```

То есть допустимо расхождение до 1 сума из-за округлений и особенностей промежуточных расчётов.

### Влияние

Даже если баланс отличается только на 1 сум, API может вернуть `balanceCheck = false`, хотя по бизнес-логике это должен быть допустимый результат.

Следствие:
- UI/Form 1 может показывать ложную ошибку по балансу
- пользователь увидит, что баланс якобы не сошёлся, хотя по правилам он допустим

### Приоритет

**Высокий.**

### Влияние

- Тест не подтверждает корректность актуального API
- возможны ложные зелёные/красные результаты при изменениях
- покрытие по Form 2 нельзя считать надёжным

### Приоритет

**Средний / высокий**, потому что это мешает безопасно проверять расчёты после исправлений.
