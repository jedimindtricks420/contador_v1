**Версия:** 2.0 (v2 активна)

**URL:** http://localhost:3032/v2 (v2) / http://localhost:3030 (v1 legacy)

---

## Что это

**contador** (исп. «бухгалтер») — SaaS-система двойной записи для малого и среднего бизнеса Узбекистана. Реализует полный цикл ежемесячного бухгалтерского учёта: импорт банковских выписок → AI-классификация → проводки → закрытие месяца → официальная финансовая отчётность (Форма №1 + Форма №2) — всё в браузере.

Соответствует **НСБУ №1** (рег. МЮ №3544, вступил в силу 01.01.2025) и **НСБУ №21** (рег. МЮ №3593, вступил в силу 01.01.2025).

## Приложения в составе проекта

### v2 — Основное приложение (порт 3032)

Документоцентричный рабочий процесс: каждая банковская транзакция превращается в Документ, Документ проводится по шаблону и создаёт проводки (JournalEntry).

```
Банковская выписка → StagedTransaction → Document → JournalEntry → Отчёты
                            ↑                 ↑
                   Правила + AI          Шаблон проводки (JSON)
```

### v1 — Legacy (порт 3030)

AI-чат: пользователь описывает операцию текстом, GPT-4o создаёт проводку. Не развивается.

### Admin-панель (порт 3031)

Express.js для управления платёжными интеграциями (Payme, Click), подписками, организациями.

## Функциональность (v2)

### 1. Мультиорганизационность
Один пользователь — несколько организаций. Переключение через `activeOrgId`. Полная изоляция данных на уровне приложения.

### 2. Импорт банковских выписок
- Форматы: 1CClientBankExchange (.txt), Excel (Asaka, Kapital, Ipak Yoli)
- SHA-256 дедупликация по полю `hash`
- Пакетный откат по `importBatchId`
- Preview-режим: первые 5 строк без записи в БД

### 3. AI-классификация (движок правил + GPT-4o-mini)

**Движок правил** (`rulesEngine.ts`):
- Приоритет: INN → KEYWORD → AMOUNT_RANGE → TREASURY_ACCOUNT
- In-memory кэш (30 сек TTL)

**AI-классификатор** (`aiClassifier.ts`):
- GPT-4o-mini, батчи до 20 транзакций
- Порог: `org.aiConfidenceThreshold` (по умолчанию 70%)
- ≥70% → `AUTO_MATCHED`; <70% → `NEEDS_CLARIFICATION`

**Очередь уточнений**: пользователь выбирает DocumentType → опция «запомнить» создаёт Rule.

### 4. Движок проводок (`postingEngine.ts`)

Единственная точка создания `JournalEntry`:
1. Разбор `DocumentType.postingTemplate` (JSON)
2. Вычисление сумм через expression evaluator (Decimal.js)
3. Создание `JournalEntry[]` в транзакции БД
4. Проверка: Σ Дт = Σ Кт
5. Создание `OpenItem` если `opensItem: true`
6. Запись `AuditLog`

### 5. Мастер закрытия месяца (7 шагов)

| Шаг | Компонент | Действие |
|-----|-----------|---------|
| 1 | Step1Import | Загрузка банковской выписки |
| 2 | ClarificationQueue | AI-классификация + ответы на вопросы |
| 3 | Step3Registry | Проверка реестра документов |
| 4 | Step4Accruals | Начисления: ФОТ, амортизация, аренда |
| 5 | Step5FxDiff | Курсовые разницы (USD ↔ UZS, курс ЦБ) |
| 6 | Step6Soliq | Сверка с реестром Soliq (ЭСФ) |
| 7 | Step7Summary | Финализация: налоги + PERIOD_CLOSING + блокировка |

**Финализация (Step 7):** `finalizePeriod()` в `closing.ts`:
- Применяет начисления из `closingData.accruals`
- Начисляет налоги (режим-зависимо):
  - VAT-режим: НДС 12%, налог на прибыль 15%
  - TURNOVER_TAX: налог с оборота по ставке `org.turnoverTaxRate` → документ `TURNOVER_TAX_ACCRUAL` (Дт 9810 → Кт 6410)
- Создаёт `PERIOD_CLOSING` (Дт 9xxx → Кт 9910 и обратно)
- Устанавливает `Period.status = CLOSED`, `Period.lockDate`
- Создаёт `TaxCalendarEvent` для следующего срока уплаты

**Годовое закрытие** (`/api/closing/year-end`):
- Только декабрь с уже закрытым периодом
- Переносит сальдо 9910 → 8710 (документ `YEAR_END_CLOSE`)
- Дт 9910 → Кт 8710 (прибыль) / Дт 8710 → Кт 9910 (убыток)

### 6. Форма №1 — Бухгалтерский баланс

**API:** `GET /api/reports/balance?to=YYYY-MM-DD`  
**Страница:** `/v2/reports/balance`

- Полный набор строк 010–780 по НСБУ №21
- Прямые SQL-агрегаты по всем `JournalEntry` до `endDate`
- Контрарные счета: 0200, 4910, 2980, 8600 вычитаются из соответствующих групп
- Строка 450 = `balCredit("8710") + transitNet`
  - `transitNet` = Кт−Дт всех TRANSIT-счетов (незакрытый текущий финрезультат)
  - transitNet > 0 → прибыль (добавляется к капиталу)
  - transitNet < 0 → убыток (вычитается из капитала)
- Балансовый контроль: `|line400 − line780| ≤ 1`

### 7. Форма №2 — Отчёт о финансовых результатах

**API:** `GET /api/pnl?from=YYYY-MM-DD&to=YYYY-MM-DD`  
**Страница:** `/v2/pnl`

- Полный набор строк 010–270 по НСБУ №21
- Прямые SQL-агрегаты по оборотам 9xxx за период (без PERIOD_CLOSING)
- Строка 250: дебет 9810 (налог от прибыли/с оборота); если 0 — фолбэк на TaxCalendarEvent
- Помесячный разрез для графиков дашборда
- Динамическая подпись налога: `Налог на прибыль (15%)` или `Налог с оборота (N%)`

### 8. Прочие отчёты

| Отчёт | Маршрут | Описание |
|-------|---------|---------|
| ОСВ | `/v2/reports/osv` | Оборотно-сальдовая ведомость с суб-аналитикой |
| Журнал | `/v2/reports/journal` | Хронология проводок |
| Карточка счёта | `/v2/reports/account-card` | Обороты и сальдо по одному счёту |
| Субконто | `/v2/reports/subconto` | Разбивка по контрагентам |
| Анализ счёта | `/v2/reports/account-analysis` | Корреспонденции счёта |
| Cashflow | `/v2/cashflow` | Движение по расчётным счетам |

### 9. Открытые позиции

- Мониторинг авансов, подотчётных сумм (командировочные 4220 и общехозяйственные 4230), депозитов (4890), дивидендов к оплате (6610)
- Автоматический статус RISK при истечении дедлайна (`RISK_DAYS_BY_ACCOUNT` / `RISK_DAYS_DEFAULT`, переопределяемо на уровне организации)
- Ручное закрытие и повторное открытие

### 10. Налоговый календарь

- Шаблоны сроков уплаты (ежемесячно / ежеквартально / ежегодно)
- Автоматическое создание TaxCalendarEvent при закрытии периода
- Дашборд: ближайшие 5 сроков + статус оплаты

### 11. Безопасность

- JWT в HTTP-only cookie (`v2_session`), срок 7 дней
- bcryptjs — хеширование паролей
- Middleware — защита всех маршрутов кроме публичных
- Изоляция тенантов: каждый запрос фильтруется по `orgId`
- Роли: `OWNER` (полный доступ), `ADMIN` (управление орг.), `ACCOUNTANT` (только данные)
